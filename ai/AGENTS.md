# AI 작업 규칙

저장소 루트의 AGENTS.md와 Git 컨벤션을 따르며, AI 작업에는 다음 규칙을 추가로 적용한다.

## 작업 범위

- 구현·테스트·AI 사용 문서는 ai 폴더 안에서만 변경한다.
- 개인 기획·백로그·진행 상태 문서는 Git에 등록하지 않는다. 작업 상태는 Jira에서 관리한다.

## 브랜치와 커밋

- 1 Story = 1 Branch = 1 MR을 유지한다. Story의 Task마다 별도 브랜치를 만들지 않는다.
- 1 논리 구조 = 1 Commit을 기본으로 한다. Task 크기와 관계없이 변경 목적과 책임이 다른 논리 구조는 각각 커밋하여 리뷰 범위를 명확하게 한다.
- 큰 기능 묶음보다 리뷰어가 한 번에 검토할 수 있는 세부 책임을 커밋 단위로 삼는다. 예를 들어 인증, 입력 검증, 시간 예산, 자원 정리, 외부 어댑터 연결은 독립적으로 검토 가능한 경우 각각 분리한다. 같은 파일도 책임이 다르면 여러 커밋으로 나눈다.
- 테스트도 해당 구현 책임과 검증 목적에 맞춰 나누며, 서로 다른 검증을 Task 전체 테스트 커밋 하나로 다시 묶지 않는다. 커밋 개수나 줄 수를 고정하지 않고 중간 단계의 실행 가능성과 리뷰 용이성을 우선한다.
- 분할 기준은 파일 수나 줄 수만이 아니라 변경 목적과 검증 가능성이다. 각 구현 커밋은 논리적으로 완결된 코드와 필요한 사용 문서를 포함한다.
- 테스트 파일의 추가·수정은 구현 코드와 별도 커밋으로 분리한다. 관련 테스트 전용 Fixture·설정 변경도 테스트 커밋에 포함하며, 테스트 커밋은 `test: [해당 Task Jira 키] <한글 명사형 제목>` 형식으로 작성한다.
- 구현과 테스트는 같은 Task에서 관리하되 서로 다른 커밋으로 기록한다. 두 변경을 검증한 뒤 기존 실행·테스트가 깨지지 않는 의존 순서로 커밋하고, Task는 관련 테스트 검증까지 끝나야 완료한다. 기존 테스트 수정이 없으면 중간 커밋이 실패하는 경우에는 호환 가능한 구현 단계로 나누며 실패 상태를 완료된 커밋으로 남기지 않는다.
- 분할한 커밋도 각각 해당 Task의 Jira 키를 대괄호로 포함한다. 예: `feat: [S15P21A207-228] FDS 입력 데이터 계약 구현`.
- 커밋 메시지는 타입, 대괄호로 감싼 Jira 키, 한글 명사형 제목 한 줄로 작성한다. 커밋 전에 예정 메시지와 분할 단위를 사용자에게 보여준다.
- 구현과 검증을 마친 작업은 사용자가 별도로 요청하지 않아도 자동으로 커밋한다. 커밋 메시지·분할 단위를 먼저 알리는 절차는 유지한다.
- Story 병합은 기존 MR·Squash Merge 규칙을 따른다. 커밋을 나누더라도 Story의 작업 범위를 확대하지 않는다.

## Task 사전 검토

- 새 Task는 제목·작업 범위·완료 기준·선행 관계와 구현/테스트 커밋 구성을 먼저 사용자에게 보여준다. 사용자의 검토·승인 후 Jira에 등록하고 구현을 진행한다.
- Task 개수는 고정하지 않고 독립적인 결과물과 검증 가능성을 기준으로 정한다. 테스트 커밋을 분리하기 위해 별도의 테스트 Task를 일률적으로 만들지 않는다.

## Draft MR과 사용자 검증

- Draft MR의 테스트 항목은 최초 목록과 검증 내용을 유지한다. 중대한 오류나 범위 변경이 없다면 항목을 추가·삭제하거나 검증 문구를 변경하지 않는다. 추가 검증 결과는 별도로 기록한다.
- 각 테스트 체크박스 문구 바로 옆에 `(관련 Task: S15P21A207-264)`처럼 관련 Task의 Jira 키를 표시한다. 여러 Task가 연결되면 키 목록 또는 범위를 표시한다. 별도 연결표만으로 대신하지 않으며, 이 Task 표기는 보완할 수 있다.
- 테스트 체크박스는 사용자가 직접 검증 후 체크한다. 에이전트는 체크 상태를 변경하지 않는다.
- Task 구현을 마치면 완료 기준별 직접 검증 명령, 실행 위치와 예상 결과를 사용자에게 안내한다. 에이전트 검증 결과와 사용자가 직접 검증한 결과를 구분한다.
